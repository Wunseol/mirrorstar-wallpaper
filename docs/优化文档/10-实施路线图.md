### 1.3 v4.0 核心目标

1. **修复全部 18 项 High**：消除资源泄漏、状态不一致、测试副作用等高风险问题
2. **统一修复策略**：解决同类问题在不同模块的修复不一致（速度校验/崩溃检测/请求序号取消/错误处理）
3. **推进 46 项 Medium**：提升健壮性与可维护性，按模块批量处理降低上下文切换成本
4. **择机处理 61 项 Low**：命名/魔法数/注释等可维护性改进，不阻塞发布

|--------|-----|------|

## 7. 风险与回滚策略

### 7.1 高风险修复项

| 项 | 风险 | 缓解措施 |
|----|------|----------|
| C-001 | 修改 dirty 标志逻辑可能影响热重载 | 保留 N-005 的 save_mutex 修复，仅调整 dirty 设置时机；新增并发测试 |
| A-001 | 实现 IMMNotificationClient 涉及 COM 回调，复杂度高 | 独立分支开发，充分测试；可降级为轮询方案 |
| W-004 | pause_all 部分失败回滚逻辑复杂 | 优先实现"保留 bit + 清理失败 sender"方案，避免过度回滚 |
| WP-001 | Pause/Resume 重构可能引入回归 | 先补全 WP-002/003 的错误处理，再做提取；保留原逻辑作为参考 |

### 7.2 回滚策略

- 每个 finding 独立提交（commit message 含 finding ID，如 `fix(C-001): ...`）
- 每个 Wave 完成后打 tag（`v4.0-wave1`、`v4.0-wave2`、`v4.0-wave3`）
- 单个 finding 修复引入回归时，可独立 revert 而不影响其他修复
- Wave 1 全部完成后进行集成测试与手动验收，确认无回归再进入 Wave 2

### 7.3 验证清单（每 Wave 通用）

- [ ] `cargo test --workspace` 全绿
- [ ] `cargo clippy --workspace --all-targets -- -D warnings` 零警告
- [ ] `npm run build` 成功
- [ ] `npm run lint` 零错误
- [ ] `npm run typecheck` 零错误
- [ ] `npm run test`（vitest）全绿
- [ ] 新增测试覆盖修复项的失败路径
- [ ] 手动验收：壁纸设置/暂停恢复/多显示器/视频/网页/GIF 主流程无回归

## 10.10 v8.0 深度内存优化（2026-07-28）

← [返回索引](./README.md)

### 10.10.1 背景

项目已完成 v4.0/v5.0/v6.0 与 NFR 优化（暂停态内存 17.14MB 达标），但运行时测试发现**设置动态壁纸后任务管理器显示 400MB+ 内存**。深度代码研究定位 5 个根因：

1. **WebView2 主窗口泄漏**（根因 #1）：`src-tauri/src/lib.rs:726` 使用 `window.hide()` 而非 `destroy()`，WebView2 子进程树（~150-300MB）常驻

4. **Tokio Runtime 默认配置**（根因 #4）：worker 线程数 = CPU 核数
5. **Image 像素数据未释放**（根因 #5）：首次绘制后 pixels 仍驻留

## 10.11 v9.0 性能优化（2026-07-28）

## 10.12 v10.0 内存优化（2026-07-28）

← [返回索引](./README.md)

> 本章节记录 v10.0 子进程内存深度优化。spec：`.trae/specs/memory-optimization-v10-2026-07-28/`。
> v8.0 Job Object 设 256MB 上限防 OOM，v10.0 聚焦**降低子进程实际占用**。

### 10.12.1 背景

v8.0 通过 Job Object 将 mpv/wp-proc 子进程内存上限设为 256MB，但深度研究发现子进程**实际占用**仍偏高：

1. **mpv 默认缓存 ~75MB**：`build_mpv_args` 未设 `--cache`，mpv 默认 `--cache=auto` 为 demuxer 分配 ~75MB。壁纸无限循环播放，seek 缓存无意义。
2. **WebView2 缓存无限制**：`create_webview` 用无 options 版 `CreateCoreWebView2Environment`，未设 UserDataFolder 与磁盘缓存上限。
3. **v9-A GIF 预取 5 帧瞬时峰值**：4K GIF 每帧 ~6MB，5 帧预取瞬时 30MB。

## 10.13 v11.0 内存优化（2026-07-28）

### 10.13.1 背景

1. **mpv demuxer 读取缓冲**：v10-A 的 `--cache=no` 禁用 demuxer cache，但 `--demuxer-max-bytes`（默认 50MB）和 `--demuxer-max-back-bytes`（默认 30MB）仍可能保留读取缓冲

4. **Tokio 运行时默认 worker_threads 过多**：`rt-multi-thread` 默认 `num_cpus` 个 worker（8 核 = 8 线程 × 2MB 栈 = 16MB），壁纸应用 IO 密集非 CPU 密集

## 10.14 v12.0 内存优化（2026-07-29）

### 10.14.1 背景

v11.0 完成后深度审查发现 2 个长期运行泄漏（peak memory 不变，但随增删/切换操作累积）：

1. **前端 `lowercasedFileNameCache` 不清理删除壁纸条目**：`Map<file_path, lowercased_name>` 在 `removeWallpaperCard` 时不同步 `delete`，全量刷新时仅增量 `has` 检查后写入而不清理过期条目。长期增删壁纸后缓存与 `appState.allWallpapers` 状态不一致
2. **后端 `VolumeControl::session_cache` 进程退出后不清除**：`HashMap<u32 pid, IAudioSessionControl2>` 仅在音频设备变更触发 `refresh_session_manager` 时 `clear()` 全量清空。壁纸进程退出（移除/切换壁纸）后 PID 条目与 COM 接口指针持续占用内存

虽然单条目占用很小（前端 ~200 字节 / 后端 ~几 KB），但长期使用下影响稳定性：100 次增删累积 ~20KB / 50 次切换累积 ~几百KB。

## 10.18 v16.0 跨模块契约与 API 一致性深度审查（2026-08-01）

> 本章节记录 v16.0 跨模块契约与 API 一致性深度审查。spec：`.trae/specs/deep-review-v16-2026-08-01/`。
> v4-v15 多轮审查聚焦"代码内部正确性"与"运行时资源安全"，v16.0 填补"跨模块边界契约 / 外部可观测 API 一致性 / 错误消息 / 依赖构建"四个盲区。

### 10.18.1 背景

项目已完成 v4.0/v4.1（正确性 268 项）、v5.0（性能 29 项）、v6.0/v7.0（技术债 201 项）、v8-v14（内存优化三轮闭环）、v41-B-001（panic=abort）、v15.0（并发/回归/降级/Win32 四维审查 + 3 项修复）多轮深度优化。当前代码状态：cargo check 通过 / clippy 零警告 / 测试全绿。

然而前几轮审查聚焦**代码内部正确性**与**运行时资源安全**，未系统审查**跨模块边界契约**与**外部可观测 API 一致性**：

1. **跨模块契约**：Tauri command ↔ 前端 invoke ↔ wp-proc IPC 协议三层契约对齐，多轮重构（v6 模块化 / v9-B 预热池 / v10 WebView2 options）后是否仍保持契约一致？
2. **API 一致性**：24 个 Tauri command 的命名风格、参数顺序、错误返回结构、前端 wrapper 命名转换是否统一？
3. **错误消息与降级**：用户可见错误消息的中英文混用、可操作性、降级路径反馈完整性。
4. **依赖与构建配置**：Cargo.lock 依赖版本安全、feature flag 最小化、CI workflow 一致性、tauri.conf.json 权限最小化。

v4.0/v4.1 聚焦原始代码正确性，v5 性能，v6/v7 技术债，v8-v14 内存，v15 并发/回归/降级/Win32。**v16 填补"跨模块契约 / API 一致性 / 错误消息 / 依赖构建"四个外部可观测维度盲区**。
