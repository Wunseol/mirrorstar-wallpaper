### 1.3 v4.0 核心目标

1. **修复全部 18 项 High**：消除资源泄漏、状态不一致、测试副作用等高风险问题
2. **统一修复策略**：解决同类问题在不同模块的修复不一致（速度校验/崩溃检测/请求序号取消/错误处理）
3. **推进 46 项 Medium**：提升健壮性与可维护性，按模块批量处理降低上下文切换成本
4. **择机处理 61 项 Low**：命名/魔法数/注释等可维护性改进，不阻塞发布

## 5. 并行实施可能性

### 5.1 完全可并行（无共享文件）

以下 Wave 1 项分布在完全不同的模块/文件，可由多个开发者或多个子代理并行实施：

| 并行组 | 项 | 理由 |
|--------|-----|------|
| **组 α** | C-001 / C-002 / C-003 | 均在 config 模块但不同函数，冲突可控 |
| **组 β** | D-001 / D-002 / ST-001 / B-001 | desktop / src-tauri / build-infra 完全独立 |
| **组 γ** | A-001 / I-001 / P-001 | audio / ipc / process 三个独立模块 |
| **组 δ** | W-001→W-002 / W-003 / W-004 | wallpaper 内部，W-003/W-004 与 W-001/002 不同文件 |

### 5.2 串行约束

| 串行链 | 理由 |
|--------|------|
| W-001 → W-002 | 共用 `duplicate_process_handle` RAII 封装 |

## 7. 风险与回滚策略

### 7.1 高风险修复项

| 项 | 风险 | 缓解措施 |
|----|------|----------|
| C-001 | 修改 dirty 标志逻辑可能影响热重载 | 保留 N-005 的 save_mutex 修复，仅调整 dirty 设置时机；新增并发测试 |
| A-001 | 实现 IMMNotificationClient 涉及 COM 回调，复杂度高 | 独立分支开发，充分测试；可降级为轮询方案 |
| W-004 | pause_all 部分失败回滚逻辑复杂 | 优先实现"保留 bit + 清理失败 sender"方案，避免过度回滚 |
| WP-001 | Pause/Resume 重构可能引入回归 | 先补全 WP-002/003 的错误处理，再做提取；保留原逻辑作为参考 |

### 7.2 回滚策略

- 每个 finding 独立提交（commit message 含 finding ID，如 `fix(C-001): ...`）
- 每个 Wave 完成后打 tag（`v4.0-wave1`、`v4.0-wave2`、`v4.0-wave3`）
- 单个 finding 修复引入回归时，可独立 revert 而不影响其他修复
- Wave 1 全部完成后进行集成测试与手动验收，确认无回归再进入 Wave 2

### 7.3 验证清单（每 Wave 通用）

- [ ] `cargo test --workspace` 全绿
- [ ] `cargo clippy --workspace --all-targets -- -D warnings` 零警告
- [ ] `npm run build` 成功
- [ ] `npm run lint` 零错误
- [ ] `npm run typecheck` 零错误
- [ ] `npm run test`（vitest）全绿
- [ ] 新增测试覆盖修复项的失败路径

## 10.10 v8.0 深度内存优化（2026-07-28）

← [返回索引](./README.md)

> spec：`.trae/specs/deep-memory-optimization-v8-2026-07-28/`。本轮聚焦**活跃态内存结构优化**（与 v4.0 正确性 / v5.0 性能工程 / v6.0 技术债并列、互不冲突），解决动态壁纸后任务管理器 400MB+ 问题，定位 5 个根因：① WebView2 主窗口 `window.hide()` 而非 `destroy()`（`src-tauri/src/lib.rs:726`，子进程树 ~150-300MB 常驻）；② 子进程无 Job Object 上限；③ GIF 全帧驻留（`DEFAULT_MAX_GIF_MEMORY_MB=40`）；④ Tokio worker 线程数=CPU 核数；⑤ Image 像素数据首次绘制后未释放。NFR"暂停态内存 < 20MB"要求的窗口销毁由 v8-A 补完。

## 10.11 v9.0 性能优化（2026-07-28）

← [返回索引](./README.md)

> spec：`.trae/specs/performance-optimization-v9-2026-07-28/`。v8.0 将内存从 400MB+ 降至 <200MB，本轮聚焦**CPU 与启动延迟**，解决 v8-C 副作用与网页壁纸冷启动慢。背景：① GIF 播放卡顿（v8-C 副作用：`decode_gif_frame_at` 每次从第 0 帧顺序解码 O(N)，100+ 帧跨 5 帧窗口触发完整文件 I/O）；② wp-proc WebView2 冷启动 5-15s、IPC 重试 40×200ms=8s 兜底；③ IPC 重试抖动 200ms。

#### Wave v9-B: wp-proc 预热启动池（P1）
- ⚠️ 已废弃：该机制因"进程收束"决策被移除，Web 壁纸改为每次纯冷启动（5-15s，前端 wallpaper-loading 进度提示兜底），以下仅历史记录。`web.rs` 新增 `WarmWpProc` + `play_with_warm` + `spawn_warm`；`manager.rs` `construct_renderer` 接收 warm 参数；`state.rs` 新增 `wp_proc_pool` + `take_warm_wp_proc` + `refill_warm_pool`；`lib.rs` setup 调 `refill_warm_pool`；`commands/wallpaper.rs` 取预热进程并补充。历史效果：网页壁纸启动 5-15s→<2s（预热命中）；降级路径保留 8s 兜底。
