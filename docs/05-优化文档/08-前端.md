## 模块概览 / 现状

> 综合自 v4.0 审查（`09-frontend.md`）与 v6.0 技术债审查（前端模块，2026-07-25）

### 模块职责

前端模块负责壁纸应用的全部 UI 渲染与用户交互：壁纸列表渲染（懒加载 + 增量更新 + 事件委托）、配置面板双向同步、显示器下拉填充、拖拽/对话框添加壁纸、预览模态框（含焦点陷阱与安全加固）、IPC 调用封装（带超时与错误脱敏）、应用级状态管理、事件监听器清理。模块采用 Tauri v2 + TypeScript，通过 `main.ts` 集中绑定所有 UI 事件，UI 子模块仅导出渲染/业务函数（v41-F-016 文档化约定）。

### 技术方案与核心结构

- **技术方案**：无框架纯 TypeScript + 原生 DOM 操作 + Tauri v2 IPC
- **核心结构**：IPC 封装层（invoke 包装函数）、壁纸列表渲染（refreshWallpaperList + renderWallpaperList + 骨架屏 + 懒渲染 + 事件委托 + 增量更新）、预览模态框（openPreview/closePreview + 焦点陷阱）、拖放（onDragDropEvent 原生文件路径处理）
- **设计模式**：
  - **F12 序号取消机制**：`refreshWallpaperList` 与 `updatePlaybackButtons`（F-001）均引入请求序号，过期响应丢弃
  - **F05 IntersectionObserver 懒渲染**：视口内卡片懒渲染 + rootMargin 200px 预加载
  - **F09 invokeWithTimeout 超时封装**：`Promise.race([invoke, timeoutPromise])` + finally 清理定时器（F-003），覆盖慢命令
  - **F-010 监听器清理约定**：`listenWithCleanup`/`addEventListenerWithCleanup` 统一登记清理函数，`cleanupAllListeners` 批量释放
  - **F-002 patchChain 串行化**：config-panel.ts 用 patchChain 串行化读改写，避免并发配置更新竞态
  - **state.ts getter/setter 封装**：selectedDisplayId 校验封装
  - **v5.0 F-PERF-001/003/015、A-PERF-001**：事件委托、template.cloneNode、元素缓存、增量事件处理
  - **sanitizeErrorMessage 脱敏**：ipc.ts 对路径/错误码/堆栈脱敏
  - **beforeunload 提前注册**：main.ts 在 init 开头注册 cleanupAllListeners，避免初始化中途失败导致监听器泄漏
- **安全方面**：所有用户可控数据（文件路径、壁纸类型）均通过 `textContent` 或 `setAttribute` 渲染，无 `innerHTML` 注入动态内容的风险；iframe 使用 `sandbox`（index.html 为 `sandbox=""`，openPreview 时显式覆盖为 `allow-scripts allow-same-origin` 运行脚本）；`sanitizeErrorMessage` 防止后端错误细节泄露到 UI

### 测试覆盖

前端测试覆盖较为完整（208+ 测试），每个源文件均有同名 `.test.ts` 配套。测试采用 Vitest + jsdom，覆盖正路径、错误分支、a11y 断言、事件委托、增量更新等。涉及真实 Win32/IPC 的失败分支通过 mock 验证调用契约（命令名、参数结构），无法在 CI 中触发真实后端失败。`ipc.ts`/`wallpaper-list.ts`/`listeners.ts`/`utils.ts` 覆盖优秀；`config-panel.ts` 测试偏少。性能优化（F-PERF-001 事件委托、F-PERF-003 template.cloneNode、F-PERF-015 元素缓存、A-PERF-001 增量更新）均有对应测试断言。

### 审查重点说明

前端架构清晰，模块边界明确，依赖方向无环（`main.ts → ui/* → ipc → types`，`state → types`，`utils/logger` 无依赖）。v3.x 修复质量整体较高：F12（序号取消）、F05（observer disconnect）、F09（超时封装）、F-010（监听器清理约定）、F-002（patchChain 串行化）均有充分注释与测试覆盖。本次审查聚焦于**同一类问题在不同模块的修复不一致**：F12 仅应用于 `refreshWallpaperList`，未覆盖 `updatePlaybackButtons`；F09 仅覆盖 3 个慢命令，未覆盖 `addWallpaper` 等潜在慢命令；F05 的 disconnect 逻辑完整，但被移除卡片内的 `<video>` 资源未显式释放。

### [F-001] [Medium] [并发] main.ts:72-90, 110-113, 429-434 — `updatePlaybackButtons` 缺乏 F12 式请求序号取消机制，并发调用产生竞态

> **状态**：✅ 已修复（代码核验通过）——main.ts 引入模块级 `let playbackSeq = 0`，入口 `const mySeq = ++playbackSeq`，await 返回后 `if (mySeq !== playbackSeq) return`；`wallpaper-state-changed` 事件追加 150ms 防抖（`debouncedUpdatePlayback`）合并连续事件。

**描述**：`updatePlaybackButtons` 是异步函数（内部 `await getWallpaperState`），但缺乏 F12 式的请求序号取消机制。在两个调用点可能产生竞态：

1. **display-select change 监听器**（main.ts:107-113）：用户快速切换显示器 A→B→C 时，三次 `updatePlaybackButtons` 并发执行。若 A 的响应最慢，其结果会最后到达并覆盖 C 的按钮状态，导致 UI 显示 A 的播放状态而用户当前在 C。
2. **wallpaper-state-changed 事件监听器**（main.ts:429-434）：后端在壁纸切换/暂停/恢复时可能连续 emit 多个 state-changed 事件，每次都触发 `updatePlaybackButtons`，无去重也无序号取消。

这与 `refreshWallpaperList` 已通过 F12 解决的竞态属于同一类问题，但 `updatePlaybackButtons` 未同步应用该模式，属于 F12 修复的遗留覆盖盲区。

**影响**：按钮 disabled 状态短暂错误（如 Playing 时暂停按钮不可用，但显示为可用），用户点击后触发后端错误提示。不会导致数据损坏或崩溃。

### [F-002] [Medium] [逻辑] main.ts:340-346, display-list.ts:14-21, 48-53 — `populateDisplaySelect` 的禁用逻辑被 `updatePlaybackButtons` 覆盖

> **状态**：✅ 已修复（代码核验通过）——`updatePlaybackButtons` 入口新增 `if (!displayId) return;` 空 displayId 直接返回，尊重 F08 的禁用决策。

**描述**：`init()` 中的调用顺序导致 `populateDisplaySelect` 的禁用逻辑可能被 `updatePlaybackButtons` 覆盖。当 `getDisplays()` 返回空数组时：(1) `populateDisplaySelect` 调用 `disablePlaybackControls()`，将 pause-btn/resume-btn 的 `disabled` 设为 `true`；(2) 紧接着 `updatePlaybackButtons("")` 被调用，若后端对 `displayId: null` 返回 `null`（无活跃壁纸），`updatePlaybackButtons` 执行 `pauseBtn.disabled = false; resumeBtn.disabled = false`，**直接覆盖步骤 1 的禁用状态**。

这与 F08（display-list.ts:42-47 注释「控件在下次成功 populateDisplaySelect 时不会被自动恢复」）的设计意图矛盾。F08 期望禁用持续到页面刷新，但 `updatePlaybackButtons` 的「无活跃壁纸则启用」规则与之冲突。

**影响**：无显示器场景下 pause/resume 按钮可能变为可点击，用户点击后向后端发送 `displayId: null` 的暂停/恢复命令，行为依赖后端实现。

### [F-003] [Medium] [资源] ipc.ts:30-41 — `invokeWithTimeout` 定时器未清理，命令快速完成时定时器仍占用资源

> **状态**：✅ 已修复（代码核验通过）——`invokeWithTimeout` 用 `let timer` 捕获定时器，`try/finally` 中 `if (timer) clearTimeout(timer)` 清理。

**描述**：`invokeWithTimeout` 使用 `Promise.race([invoke(cmd, args), timeoutPromise])` 实现超时。当 `invoke` 在超时前 resolve 时，`timeoutPromise` 内的 `setTimeout` 回调仍会在 `timeout` ms 后触发（其 `reject` 落在已 settled 的 promise 上，成为 no-op）。

问题：(1) **定时器未清理**——每次 `invokeWithTimeout` 调用（即使命令快速完成）都会留下一个 `timeout` ms 后才触发的定时器。对于 `setWallpaper`（10s 超时）等高频调用，积压的定时器虽不会泄漏（回调执行后即回收），但在窗口期内占用内存与事件循环槽位。(2) **超时不取消底层 invoke**——注释已说明「超时不会取消底层 invoke」，这是 Tauri IPC 的已知限制。但超时后底层 invoke 的结果被静默丢弃，若后端操作有副作用（如 `setWallpaper` 已创建进程），前端与后端状态可能不一致。

### [F-004] [Medium] [错误处理] main.ts:283-285, 294-296, 309-312 — pause-btn/resume-btn/interaction-mode 三个 catch 块未捕获错误对象

> **状态**：✅ 已修复（代码核验通过）——三处已统一为 `catch (e) { log.error("...", e); showStatus(..., "error"); }` 模式。

**描述**：pause-btn、resume-btn、interaction-mode 三个事件监听器的 `catch` 块未捕获错误对象，丢失了调试所需的错误信息：`catch { showStatus("暂停失败", "error"); }`。对比同文件内其他监听器（如 arrangement-select:135-139、scaling-mode:164-168、volume-slider:183-186）均使用 `catch (e) { log.error(..., e); ... }` 模式，这三个监听器是明显的不一致。

**影响**：当 IPC 失败时，错误堆栈与原因仅显示给用户（「暂停失败」），未记录到 `log.error`，开发者排查问题缺少上下文。`ipc.ts` 的 `sanitizeErrorMessage` 已脱敏，但此处根本未调用 `log.error`，脱敏逻辑也未被利用。

### [F-005] [Medium] [错误处理] ipc.ts:9-11, 30-41 — F09 的 `invokeWithTimeout` 未覆盖 `addWallpaper` 等潜在慢命令

> **状态**：✅ 已修复（代码核验通过）——`addWallpaper`（30s）与 `removeWallpaper`（15s）均已改用 `invokeWithTimeout`；超时命令选择标准与分档（v41-F-014：短 10s / 中 15s / 长 30s）已文档化于 `invokeWithTimeout` doc comment。

**描述**：F09 的 `invokeWithTimeout` 仅应用于 3 个命令：`set_wallpaper`、`generate_thumbnail`、`regenerate_thumbnails`。但 `addWallpaper` 同样是潜在慢命令却未覆盖。`add_wallpaper` 后端实现通常涉及：文件复制/移动（大视频文件可能数秒）、缩略图生成、数据库写入。drag-drop.ts 的 `addAndAutoSetWallpaper` 中 `await addWallpaper(filePath)` 无超时保护，若后端卡住（如文件在 NFS/网络盘上），前端无限等待，用户无反馈。

其他未覆盖但可能有风险的命令：`remove_wallpaper`（删除大文件）、`update_config`（写配置文件，磁盘满时可能阻塞）。

### [F-006] [Medium] [资源] wallpaper-list.ts:143-162, 230-236 — `fillThumbContent` 创建的 `<video>` 元素在列表重渲染时未显式释放

> **状态**：✅ 已修复（代码核验通过）——重渲染前遍历旧 `<video>` 执行 `pause()` + `removeAttribute("src")` + `load()`；`removeWallpaperCard` 单卡片移除与 preview 的 `resetMedia` 复用 `ui/utils.ts` 的 `releaseVideoElement` 助手。

**描述**：`fillThumbContent` 为 Video 类型壁纸创建 `<video>` 元素抓取首帧（preload="metadata" + currentTime=0.1）。当 `renderWallpaperList` 重新渲染时，旧卡片通过 `grid.innerHTML = ""` 从 DOM 移除，但未显式释放 video 资源。对比 `preview-modal.ts` 的 `resetMedia()`（line 115-135）显式调用 `video.pause()` + `removeAttribute("src")` + `video.load()`。

`wallpaper-list.ts` 的 video 元素在移除 DOM 后，浏览器虽会最终 GC，但：(1) 正在进行的 metadata 加载/首帧解码不会立即中止，持续消耗网络带宽与 CPU；(2) WebView2 对移除 DOM 的 media 元素资源回收时机不保证及时。当用户频繁刷新壁纸列表时，积压的未释放 video 元素可能导致内存与解码资源峰值。

### [F-007] [Low] [可维护性] wallpaper-list.ts:29 — 骨架屏数量使用魔法数 `8`，无注释说明

**描述**：骨架屏数量使用魔法数 `8`（`for (let i = 0; i < 8; i++)`），无注释说明。该数字应与 CSS 网格布局的列数匹配，但无关联注释或常量定义，后续修改 CSS 列数时可能遗漏同步。

**修复状态**：✅ 已修复（代码核验通过）——提取 `const SKELETON_COUNT = 8` 模块级常量，与 CSS 网格列数对齐注释（wallpaper-list.ts:27）。

### [F-008] [Low] [性能] wallpaper-list.ts:272-277 — `renderWallpaperList` 逐个 `appendChild` 触发多次布局重排

**描述**：`renderWallpaperList` 在循环中逐个 `grid.appendChild(card)`，每次 append 触发一次布局重排（reflow）。对于大量壁纸（100+），逐个 append 的重排开销显著。

**修复状态**：✅ 已修复（代码核验通过）——使用 `DocumentFragment` 批量插入卡片，先捕获 children 引用再统一 observe，保持懒渲染语义（wallpaper-list.ts:489-501）。

**影响**：壁纸数量大时首次渲染略慢（毫秒级，用户感知弱）。

### [F-009] [Low] [安全] preview-modal.ts:65-73, index.html:111 — iframe `sandbox=""` 仍允许通过 HTML 标签发起外部网络请求

**描述**：Web 类型壁纸通过 `<iframe sandbox="">` 加载本地 HTML 文件。`sandbox=""`（无任何 allow-* 标志）正确禁用了脚本执行、表单提交、弹出窗口等，但仍允许通过 `<img src="external-url">`、`<link rel="stylesheet" href="external-url">`、`<video poster="external-url">` 等纯 HTML 标签发起外部网络请求。恶意 HTML 壁纸文件可通过这些标签向外部服务器泄露用户环境信息（如 IP、User-Agent、加载时机）。

**修复状态**：✅ 已修复（代码核验通过）——`openPreview` 的 Web 分支追加 F-009 安全模型说明段并加固 iframe：`referrer-policy="no-referrer"`、`sandbox="allow-scripts allow-same-origin"`、`allow="geolocation=(), microphone=(), camera=()"`（preview-modal.ts:102-118），文档化 `sandbox=""` 残留风险与缓解措施。

**影响**：低。需要用户主动添加恶意 HTML 文件为壁纸才会触发，且仅泄露浏览器层面信息（无文件系统访问权限）。

### [F-010] [Low] [并发] preview-modal.ts:198-217 — 「设为壁纸」按钮 click 处理器未在执行期间禁用按钮

**描述**：「设为壁纸」按钮（`preview-set-btn`）的 click 处理器是 async 函数，但未在执行期间禁用按钮，用户可快速连续点击触发多次 `setWallpaper` IPC 调用。对比 main.ts:393-409 的 `regenerateBtn` 处理器使用了 `regenerateBtn.disabled = true` / `finally { regenerateBtn.disabled = false }` 模式，`setBtn` 缺失此保护。

**修复状态**：✅ 已修复（代码核验通过）——click 处理器外层包裹 `btn.disabled = true` / `finally { btn.disabled = false }`（preview-modal.ts:244-263）。

**影响**：多次 `setWallpaper` 调用可能导致后端重复创建壁纸进程（依赖后端幂等性），或多次 `closePreview` 调用（首次成功后 `currentPreviewId` 置 null，后续调用提前返回，实际影响有限）。

### [F-011] [Low] [可维护性] main.ts:110-113, 430-433, 438-441 — `void IIFE().catch()` 模式重复 3 次

**描述**：`void (async () => { await ... })().catch((e) => log.error(...))` IIFE 模式在 main.ts 中重复 3 次，用于在同步事件回调中调用 async 函数并捕获错误。该模式正确但冗长，且每次重复都需手写 catch 与错误消息，易遗漏（如 F-004 的 catch 丢失错误对象）。

**修复状态**：✅ 已修复（代码核验通过）——新增 `src/scripts/utils/async-helpers.ts` 导出 `runAsync(fn, errorMsg)`，替换 main.ts 中多处 IIFE 调用。

### [F-012] [Low] [资源] listeners.ts:19-27 — `addEventListenerWithCleanup` 清理闭包捕获 target 强引用

**描述**：`addEventListenerWithCleanup` 的清理闭包捕获了 `target` 强引用：`cleanups.push(() => target.removeEventListener(...))`。清理函数存入模块级 `cleanups` 数组，直到 `cleanupAllListeners()` 调用才释放。若 `target` 是动态创建的 DOM 元素（未来场景），且该元素在页面卸载前就应被 GC，则 `cleanups` 数组中的闭包会阻止其回收，造成内存泄漏。

**修复状态**：✅ 已修复（代码核验通过）——在 `addEventListenerWithCleanup` 函数 doc comment 追加 F-012 调用方契约段落，文档化 target 生命周期约束与动态元素清理建议（listeners.ts:18-41）。

**当前使用情况**：所有现有调用点的 target 均为页面级长生命周期元素，与页面同生共死，无实际泄漏。此 finding 为 API 层面的潜在风险记录。

## 优化机会与交集汇总

### 优化机会（v6 非技术债类改进点）

- **`appState` 响应式化**：state.ts 注释提及"未来用 class + getter/setter 或 Proxy 实现自动日志/校验/响应式更新"。当前简单对象字面量在状态数量（3 个字段）下足够，若后续增加需校验的状态可评估轻量响应式方案。
- **IPC 类型自动生成**：types.ts 注释提及"引入 ts-rs 或 tauri-specta 从 Rust 结构体自动生成 TS 类型"。F-TD-005 删除的错误类型 15 个变体手动维护已有负担，可优先对错误类型引入自动生成。
- **错误处理统一**：`handleIpcError(e, statusMsg)` 辅助函数可统一 main.ts 各 catch 块反复出现的 `log.error + showStatus` 模式（约 8 处）。
- **`debounce` 泛型签名优化**：统一 `debounce<...>` 签名（当前覆盖所有调用点，可评估是否限制无参）。
- **`main.ts` init() 拆分**：`init()` 约 420 行，含 12 个事件绑定 + 6 个 listenWithCleanup。v41-F-016 已文档化"按 bindDisplayEvents / bindPlaybackEvents / bindWallpaperEvents 拆分"，事件数继续增长时应实施。
